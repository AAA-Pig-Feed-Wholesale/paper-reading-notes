01 / SOURCE READING

研究对象发生变化：不再只比两段答案

Agent Arena 官方文章将 Agent 定义为由模型与 Harness 多组件构成的工作系统：同一任务可能涉及模型编排、工具调用、子 Agent、文件与长上下文。传统 Chatbot Arena 的匿名双模型投票难以充分反映真实任务分布，更难拆开不同组件的贡献。作者因此从真实用户在 Agent Mode 的逐次会话记录提取任务信号，并通过随机化组件配置估计其贡献。官网 Intro / Methodology

核心迁移：pairwise vote（两份答案谁更好）→ point-wise trace（单次真实任务发生了什么）→ randomized comparison（配置改变带来什么差异）。

评测对象

具有工具链和 Harness 的整个 Agent 工作过程，而不只是最后一句回答。

观察数据

来自用户显式/语言反馈、纠错结果及工具执行环境；每个任务得到多个单独信号。

因果策略

随机分配组件配置，结合对照分布与加权估计“组件选择导致的净改善”。

最重要的范围限定：文章提出可扩展至多组件 Harness 的因果框架，但明确说首版生产榜单仅评价主编排模型（orchestrator），此时 K = 1；工具、系统提示、Harness 子模块的榜单仍是计划中的扩展。官网 Intro 末段 / Formal Details 末段
02 / SOURCE READING

Methodology 总流程：真实 Trace → 信号 → 因果效应

RANDOMIZE随机分配配置

会话从 P 中抽取 orchestrator / 扩展组件设置。

OBSERVE产生真实任务 Trace

记录用户反应、纠错和工具执行。

MEASURE抽取 5 类任务信号

每项信号单独计算 session/task outcome。

ESTIMATE估计净改善

对照 Q，按权重估计效应与置信区间。

官方称其方法为 Causal Tracing：不是把所有 Trace 交给一个大模型打“总体印象分”，也不是直接拿不经校正的成功率排名，而是先为每个信号计算单独效果，再将信号级结果平均为总体分数。文章提供估计目标、权重与置信区间公式。官网 Methodology / Formal Details

概念拆分：Trace 是观察材料；Signal 是从材料中提取的结果指标；Treatment 是被随机化的模型或组件选择；Effect 是对固定基线分布 Q 的预期结果变化。不要把四者混成“轨迹评分”。
03 / SOURCE READING

五个首版信号：明确“怎么判定成功”

五类信号并不等价：有些来自用户明确确认，有些是自然语言的间接反馈，也有些来自执行环境。文章强调这是首批信号，未来可能增补、修改或停用。官网 Per-Signal Leaderboards

信号官方定义 / 判断规则反映的能力需留心
Confirmed success用户在 Arena UI 标记任务成功/失败；一个 task 轨迹采用最终 approve/disapprove。明确的用户验收未反馈的人群是否具有代表性，文章未量化。
Praise vs. complaint任务内明确表扬次数超过明确抱怨次数，判定成功。语言感知的满意度语气、文化风格、沉默用户可能影响解释。
Steerability用户提出中途纠正后，Agent 尝试修正；用户接受算成功，拒绝或放弃算失败。修正能力与用户可控性样本条件是出现纠错的场景。
Bash recovery模型原因导致 bash 命令失败后，计数后续 bash 调用直到出现非错误命令；放弃则额外惩罚。工具异常后的恢复效率明确排除环境原因的命令失败。
Tool hallucination调用不存在的工具，包括虚构名称、错误字段名称或泄漏的思维文本；发生则任务判失败。工具接口可靠性工具幻觉与“工具实际效果差”不是同一指标。
成本 ≠ 第六个当前榜单信号：官方单独讨论部署后实际成本和质量—成本的 Pareto 权衡，但明确称成本不是首批综合榜单的五个信号之一。成本还会受到额外步骤及用户为了满意而多轮交互的影响。官网 Per-Signal 末段
04 / SOURCE READING

先拆清计量单位：session、task、turn、tool call

单位文章中意味着什么为什么重要
Session用户与一个 Agent 的长期会话，可包含多个 task。一个会话计数不等于任务计数，分母不能直接互换。
Task一次可完成或失败的工作目标。Confirmed success / praise / complaint 通常按 task 聚合。
Turn一次用户或 Agent 交互回合。最终 approve / disapprove 属于任务轨迹的后段反应。
Tool call实际结构化工具动作，如 bash / write_file / web search。Bash recovery 与 tool hallucination 需要工具级记录。
Trace各级交互与工具事件构成的可观察执行轨迹。包含提取各信号需要的原始证据。
完整 Agent 评测的重要性：一个 task 可能在一次 session 的多个 turn 中完成，也可能需要几十次工具动作。单看模型最后回复，会漏掉纠错、放弃、工具失败和执行成本。

06 / SOURCE READING

真实工作形态：用户如何纠错、Agent 如何声称完成

官方的行为观察表明：用户初始请求常是“交付完整工作”，看到首轮结果后反而收紧控制、追加纠正；复杂请求典型不足是漏做一个子任务。文中还定义了两个观察性标签：Bluffing（未完成却宣称完成）与 Bluster（语言上态度坚决，但在压力下未真正坚持）。官网 What People Build / How People Work With Agents

Bluffing

问题不是“回答语气自信”，而是实际产物或任务不完整与“已完成”宣称不匹配。应由 artifact/环境验收证实。

Bluster

描述语言上声称坚持，但继续追问后行为失守。属于文章观察标签，不等于已发布单独的定量排行榜指标。

切勿捏造统计：文章没有给 Bluffing、Bluster 的统一发生率、识别器精确率或因果影响数值。它们是作者从 Trace 进行的行为分析，不能填上“X% 的 Agent 会 bluff”。

关键因果定义：为何不是直接比较样本成功率？

以 K 组件 Agent 为例，每个 session i 抽样一个配置向量 Tᵢ；某组件 k 取值 t 即一次 treatment。目标分布 Q 定义作者关心的固定对照组合（通常设为均匀分布），在线抽样分布是 P。不同用户任务分布和模型上线时间变动时，原始比例可能混入配置分布变化。官网 Formal Details

τk→t = ET∼Q [ Y( Tk = t ) − Y ]潜在结果定义：如果把第 k 个组件强制设为 t，相对于 Q 下原配置的预期任务结果变化。此处的 Y 取某一个信号，五项信号分别估计后再合成。
τk→t = EQ [ Y | Tk = t ] − EQ[Y]官方在独立随机抽样组件的条件下给出的识别式。它是平均处理效应相对于“基线分布”的形式，不是和某个固定竞争对手直接打擂台。
如何理解“Net Improvement”：它是某组件选择 t 的平均结果相对指定 baseline distribution Q 的变化；不是绝对任务成功率，不等于“它比所有对手都强”，也不等于 Harness 每个子模块都已被评估。官网 Methodology / Formal Details

估计公式逐项拆开：P、Q、w 与自归一化

作者使用 self-normalized importance weighting，将来自在线分配分布 P 的会话数据转为目标分布 Q 下的加权均值，再做 treatment 与 baseline 的差。官网 Formal Details, estimator

wᵢ = ∏k=1…K qk( Tᵢ,k ) / pi,k( Tᵢ,k )每个会话的重加权比：目标分布出现此配置的概率 ÷ 在线实际分配概率；K 个独立组件时逐项相乘。
τ̂k→t = [ Σi:Tᵢ,k=t wᵢYᵢ / Σi:Tᵢ,k=t wᵢ ] − [ Σi wᵢYᵢ / Σiwᵢ ]第一项：处理条件下的加权均值；第二项：Q 基线下的总体加权均值。每项各自用权重和归一化。

P：实际抽样机制

线上一次会话实际被随机配置为什么组件的概率。它可以随会话、时间变化，公式用 pi,k(t)。

Q：固定目标分布

研究希望比较的基线组件组合概率。官方称通常采用均匀分布，避免结果只被某个时段热度与配置占比牵引。

识别前提 / 方法延伸：随机分配与其独立性由文章设定；重要性权重还需要对目标 Q 支持的配置在 P 中有非零抽样概率，否则 q / p 无法估计。极端小 p 会造成大权重与高方差，这属于统计推论的实施风险，官方本页未给相关诊断表。解释 / 方法条件

置信区间与时间漂移：作者如何处理

95% 置信区间

论文网页给出在 self-normalized estimator 的通常中心极限定理条件下，使用 τ̂ ± 1.96 × estimated SE 报告估计区间。没有提供完整 bootstrap 或 cluster robust 计算细节。

时间衰减加权

当新模型加入后，配置和任务分布会变化；作者另外给近期数据更高权重，以令榜单贴近当前表现，但页面没有给出衰减常数及具体公式。

如何读区间：若一个净改善估计值附近区间跨零，对该处理效应的方向应保留不确定性。跨零或不跨零不能替代对任务覆盖、信号质量与分配机制的检查。统计学解释

这些区间只表达在作者设定的抽样与估计模型中的统计不确定性；它们不能自动解决用户自选择参与、反馈缺失、信号误识别、平台分布迁移造成的外部效度问题。评估者分析，非文章报告的量化结果

研究设计能支持什么，证据还缺什么？

问题文章所支持的内容需要保留的不确定性
因果解释组件分配被随机化；在指定 Q 和信号下可以估计平均处理效应。没有公开多组件具体在线随机化结果；只读文章不能复现原始日志。
信号有效性五项信号可操作且分别给出定义。未给信号提取器对人工标签的精确率/召回率、缺失反馈处理统计。
样本代表性报告平台一个近期 7 天切片的真实任务分布。平台用户与更广泛企业/中文/高风险工作未必同分布。
时间影响使用时间衰减以应对新模型进入等漂移。页面未披露衰减函数、敏感性分析或详细 SE 实现。
成本权衡记录真实多步、多轮后的部署成本；成本不只看 tokens 单价。文章没有完整给出性能—成本 frontier 的数字与统一选择规则。
“因果”二字的准确读法：对已随机化的模型选择、已定义的任务群体与结果信号，推断相对 Q 的平均处理效应；并非在所有 Agent 产品上无条件隔离每个模块的因果贡献。方法解释与局限综合

一页复盘、思考问题与自测

观测材料

来自真实任务的 point-wise Trace。

结果定义

确认成功、表扬投诉、纠错、Bash 恢复、工具幻觉。

对照设计

组件随机化 P，固定目标 Q，估计净改善。

估计

Importance weighting + self-normalization。

统计不确定性

SE 与 95% 区间；时间衰减应对漂移。

现实边界

首版生产榜单 K=1，仅 orchestrator。

自测 1｜为什么不能用“两个模型实际任务成功率相减”直接等价替代处理效应？
原始样本中配置出现概率、时间段与任务构成可能变化；文章利用组件随机化与 P→Q 重加权定义相对固定基线 Q 的平均处理效应，而不是直接相减两个任意抽样子群的成功率。
自测 2｜模型调用了一个不存在的工具，但最后通过其他方式完成了工作，会被 Tool hallucination 怎样记录？
依据文章定义，发生不存在工具调用就把该任务记为失败。这是专门信号的定义，不等于其他所有信号同时必然失败。
自测 3｜官方已经完成多组件 Harness 层级的因果归因了吗？
没有。文章提供 K 组件的形式化框架，但明确当前生产榜单只有 orchestrator，K = 1；其他组件评测仍处扩展方向。
自测 4｜部署后的实际成本是五项信号之一吗？
不是。官方把它列为可额外计算的指标，用来理解任务质量与成本的 Pareto 权衡，五项榜单信号中没有成本。
继续思考：如果某个模型更爱主动询问澄清，而另一模型直接写代码，如何避免“用户更可能给前者纠错/审批”的行为差异影响信号解释？这是可以设计后续实验的问题；本文没有给定量答案。研究延伸
