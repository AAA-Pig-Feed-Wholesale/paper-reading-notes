02LangChain：不要只对最终答案打分

文章从一个容易被忽略的生产失败模式出发：Agent 最终答对了，但中间可能选错工具、无意义循环，或者产生了不安全的副作用。只观察最终回答，会把「偶然答对但路径脆弱」误判为稳定能力。作者因而将回答、工具路径、使用上下文、状态变更和对话状态视为一组共同的发布质量表面。

来自原文：开篇及 “Three levels of agent evaluation”。原文定位 ↗
结果有没有对？

输出内容是否准确、完整、符合用户目标。

过程是否合理？

工具选择、参数、检索与分支路径是否安全、有效率。

环境是否改变正确？

文件、数据库、日程或其他目标状态是否真的更新。

解读：Trace 并不等于「模型的全部内部思维」。工程上主要观察可获得的消息、工具调用、输入输出、错误、状态与耗时；不要把未记录的内部推理当成可审计事实。

03Run / Trace / Thread：三种评测粒度

LangChain 明确用三种可观测对象来对应 Agent 的不同风险位置：Run 是一次模型调用或工具操作；Trace 是 Agent 的一个完整执行轮次；Thread 汇总多轮交互。它们不是三个互斥技术，而是局部、端到端、多轮的互补视角。

Component-level

Run：定位具体决策错误

验证对象：这一步是否选对 API？工具参数是否正确？中间输出是否符合格式？文章举例，可通过 interrupt_before 等方式让 Agent 只执行到某个动作，以减少干扰。用途：工具路由、参数填充、节点级回归；局部测试快且容易归因。

示意：用户要查订单 → 只检查 Agent 是否调用 get_order(order_id)，而不是误调用退款工具。
End-to-end

Trace：一次任务要看三个维度

Final response：最终答复；Trajectory：动作序列与路径质量；State changes：实际产物及副作用。严格顺序匹配只应在顺序关乎正确性或安全时使用；允许其他有效路径，必要时给可测量的部分进展分。

示意：Agent 声称已修改配置文件，但文件没有变化。最终回复看似正确，环境状态评测应判失败。
Conversation-level

Thread：跨轮次看完整用户目标

评估整段对话的语义意图、最终任务结果和跨轮轨迹，包括上下文切换、记忆保持与纠错。文章介绍 N-1 测试：保留真实会话前 N−1 轮，让新版本只生成末轮；复杂流程可用条件式推进，避免写死整段对话脚本。

示意：用户先要求改签，再补充“不改变目的地”。末轮回复必须正确继承此前约束。

来源：LangChain · “Three levels of agent evaluation” ↗

04离线 + 线上：分工而不是替代

方面Offline Eval · 离线Online Eval · 线上
数据来源已审阅样本与参考结果；覆盖已知场景生产流量的采样 Trace / Thread
回答的问题新版本是否修复缺陷、破坏旧能力？真实用户带来了哪些未知失败或质量漂移？
典型判分规则 / 代码、参考答案 Judge、人工无参考 Judge、规则、用户反馈、抽样人工
风险测试集无法穷尽真实需求缺少可靠 Ground Truth，难直接判真实正确性
工程动作发布前回归；记录版本与实验配置监控异常、抽样复核、把失败样本回流

LangChain 建议从部分生产流量抽样以控制 Judge 成本，其文章举出 10% 采样率作为起步思路；这属于特定的实践建议，不是所有团队都适用的行业标准。文章强调：离线兜住已知问题，线上负责发现未知问题，两个方向在数据回流处闭合。

05选评估器：可验证的问题尽量不用主观 Judge

评分方式适用判断风险 / 边界
Rule / CodeJSON Schema、路径、状态写入、工具名、参数约束、程序单测规则能识别的范围有限；表面匹配不等于语义正确
LLM-as-a-Judge帮助性、忠实度、表达适宜性、轨迹是否合理等语义标准存在偏差、尺度漂移；须校准并记录理由
Pairwise同一个数据集上比较版本 A/B 的质量倾向需控制顺序、样本与评价标准，不能直接证明绝对正确
Human / Expert高风险、歧义、业务专门知识和 Judge 校准成本高且人之间也会意见不一，需要规范与复核

LangChain 倡议对于清晰的通过条件，优先使用二元通过/失败信号，以降低 1–5 分尺度的解释歧义；对其 LLM Judge，从至少约 20 条已标注样本开始校准并持续补充。这是文章提供的起步经验，不意味着「20 条就足够统计验证」。

火山引擎的 AgentKit 公共文档将评估器区分为 LLM Evaluator 与 Code Evaluator，同时支持预置 / 自定义、得分理由及人工校准；它允许通过固定评测对象而切换评估器版本，分析「评判器本身有没有变好」。

分别来自：LangChain · “Calibrating the judges” ↗ · AgentKit · 自建评估器 ↗

06人工不是完全退出，而是变成校准与兜底

LangChain 把人工复核放在有价值的子集：线上负向分、用户投诉、复杂边界情况、法律医疗金融等需要专门知识的领域，或者新 Judge 的校准样本。人工纠正形成两类资产：正确示例 / Golden Labels 和 Judge 的校准数据。

01 发现线上 Trace 异常 / 用户反馈
02 路由进入人工标注与复核
03 定义形成明确可验证的预期
04 回流加入评测集；同步校准 Judge
05 回归新版本必须再次通过

来源：LangChain · “Human review that scales” / “Closing the loop” ↗

关联前面论文的认识：Judge 与人工的一致率不等于真实正确率；自动 Judge 的目的不是无条件取代人工，而是将可标准化判断扩大覆盖，把有限人工资源留给疑难任务和质量标尺维护。

07火山引擎 AgentKit：把评测过程组织为三个对象

AgentKit 官方公开的评测产品结构非常清楚：评测集（Dataset）＋评估器（Evaluator）＋实验（Experiment）。与其记平台菜单，不如理解三者在工程里分别承载什么、如何控制版本。

Dataset

评测集

包含 input 和可选的 reference_output；支持自定义数据列、字段类型、历史版本与关联实验。样本设计应覆盖核心链路、难度分布、异常输入及线上失败案例。

Evaluator

评估器

可用 LLM Prompt 定义语义规则，或用 Python / JS 代码执行确定性检查；提供得分与理由，可测试并提交评估器版本；部分评分支持人工校准。

Experiment

实验

在选定数据集及版本上评测 Agent 的输出，组合一个或多个评估器；汇总逐样本明细、指标得分、性能与成本，支持同一评测集上比较不同实验。

官方证据：评测概述 ↗ · 评测集 ↗ · 评估器 ↗ · 实验 ↗

评测集最应学习的是“覆盖设计”，不是导入按钮

AgentKit 文档强调典型交互、不同领域 / 难度、异常及违规输入，并建议将用户反馈中不合理的响应回流进测试集。参考答案并非对任何开放任务都必须存在；没有唯一标准答案时，应转而定义可检验的任务约束、状态断言或明确的评分规则。

评估器更应学习“独立版本化”

对比 Agent 版本时应尽量固定 Judge；若在优化 Judge，就保持被测输出不变，以免评分变化同时来自系统质量和评判标准变化。AgentKit 文档将两种迭代方式分别列举，说明评判器本身也是需要持续评估的对象。

08实验结果不止平均分：还需会话与行为分析

AgentKit 的评测实验将逐样本输入、实际输出、评分和理由汇聚为报告；相同评测集关联的实验可以按评估器指标对比。其公开「会话分析」与「评估打标」文档进一步描述将消息、完整会话、Trace 和打标结果统一下钻，对 Token、耗时、用户体验与具体异常进行分析。

公开模块能帮助回答的问题需要避免的误读
实验明细 / 指标哪些样本失败？什么指标下降？是否伴随成本增加？总体均分掩盖了关键业务子群、边界条件
Trace / Session 关联失败发生在哪一轮、哪个工具、哪个节点？有 Trace 不等于已识别真正原因
评估打标准确性、完整性、幻觉、安全、态度等如何分维度观察？多个评分维度并非自动经过信度校验
满意度 / 情绪分析用户体验恶化集中在哪些会话与阶段？代理指标不等同于任务真实完成率
官方证据：评测集关联实验 ↗ · 会话分析概述 ↗ · 评估打标概述 ↗
产品文档 ≠ 内部业绩披露。这里可以确认「公开产品支持这类评测机制」，不能据此断言其客户的实际准确率、线上降本幅度或任何未经披露的生产规模。

10抽取一条不依赖平台的工业评测闭环

结合两份资料可推导出一个可迁移的工作流。它不要求使用 LangSmith、AgentKit 或 Langfuse；平台只负责承载其中的数据与流程。

01 定义合同任务目标、关键约束、可观察成功条件
02 建立样本典型 / 困难 / 反例 / 线上失败，保存标签
03 采集证据输出、工具动作、实际状态、成本与耗时
04 分层判分规则 / 执行验证 / Judge / 专家复核
05 比较与回流固定条件评估改动，失败升级回归集

每条样本最小信息契约 解读

case_id、input、context_snapshot、expected_behavior / reference、scenario_tags、evidence、model_version、harness_version、judge_version。

这是便于复现实验的建议字段，非厂商统一 schema。

最小报告应回答 解读

样本覆盖是否代表目标人群？任务完成了多少？哪些关键场景失败？问题起于哪个步骤？改动后是否改善？成本和延迟有没有不可接受的代价？Judge 与人工是否一致？

建议同时展示分组结果和具体失败案例，而非只有总分。

层级可验证条件评分方式

层级可验证条件评分方式

12实践边界：容易把评测做“看起来很完整”的地方

有 Trace ≠ 有 Eval

追踪记录告诉你「发生了什么」，只有任务标准与证据对应后才能判断「该不该这样做」。

高 Judge 分 ≠ 真实正确

LLM 评分有偏差；客观状态、真实执行和人工标注不能只用另一轮 LLM 替代。

路径相异 ≠ 失败

在允许多解的任务里，对固定工具顺序硬匹配会误伤合法策略；安全必需序列则应严格断言。

平均值改善 ≠ 所有人都改善

边界情形、关键客户群与高风险动作应单独拆分；必要时报告置信区间与重复实验。

修 Agent 与修 Judge 要分开

比较 Agent 版本时固定数据与评判口径；改评估器时使用固定输出及人工样本重新校准。

线上无参考 ≠ 可以随便判真伪

没有 Ground Truth 时优先发现危险、漂移和异常；对正确性做强结论前必须补充可验证证据。

13一页复盘：从论文到工业实践衔接在哪？

之前的学术知识工业实践承接点
Agent Evaluation Survey把 Outcome、过程、任务与系统指标拆成实际的 Run / Trace / Thread 和业务维度
LLM-as-a-Judge选择 Judge / Code / Human；把偏差、人工一致性、校准变成评估器维护流程
Arena-Hard / BenchBuilder不只关心评分器，还要维护样本覆盖、困难度、版本与评测集可信度
Agent-as-a-Judge让评价依托文件、环境状态、轨迹证据与分层需求，而非单一最终回答
Agent Arena区分系统改动与结果变化的相关性；有条件时再设计随机对照或因果评估

研究资料结束后，应留下的 6 个问题

  1. 真正的成功条件可否被外部证据验证，而不是靠 Agent 自述？
  2. 在哪个粒度发现问题，又在哪个粒度诊断原因？
  3. 选择什么样的评估器；哪类问题不能交给 LLM Judge？
  4. 数据集来源、覆盖、版本和判分标准是否固定？
  5. 如何说明“新版本更好”不是数据分布或 Judge 变化导致？
  6. 线上失败如何成为未来每次发布前必须通过的测试？
一句话记忆：生产 Agent 评测不是一个 Dashboard，也不是一个 LLM Judge，而是围绕目标、证据、评判器、实验与反馈构建的持续质量控制机制。
