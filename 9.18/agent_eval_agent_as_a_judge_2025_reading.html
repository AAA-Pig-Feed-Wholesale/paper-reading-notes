01 / RESEARCH QUESTION · PDF pp.1–3

从结果评分到 Agent Judge：论文解决什么问题？

《Agent-as-a-Judge: Evaluate Agents with Agents》并非简单地把“给两段回答打分”的提示词换成“给 Agent 打分”。作者认为，Agent 的完整任务涉及多个动作、文件和中间里程碑，只看最终成功率容易丢失诊断信息；若逐步人工检查又会非常昂贵。论文由此提出：让具有工具与环境访问能力的 Judge Agent，针对细粒度需求主动采证，再判断是否满足。p.1 摘要；§1

55
DevAI 真实风格 AI 开发任务
365
具备依赖关系的硬性 Requirements
125
独立记录的软性 Preferences
核心问题不是“Judge 能不能给项目一个总分”，而是“Judge 能否像开发者验收一样，检查工作区与执行证据，指出任务流程中具体哪项需求成功或失败”。
证据范围先说清：文章在 55 个 AI 开发任务、3 个历史版本代码 Agent、特定 Judge 模型上给出概念验证；未证明所有类型 Agent、所有业务和所有模型的通用性能。论文最后把跨领域迁移列为讨论，而不是已完成的跨领域实验。pp.1–3,9
02 / FIGURE 1 · PDF p.2

Figure 1：LLM、Agent、Human 三种 Judge 到底差在哪？

LLM-as-a-Judge

模型阅读给定文本与候选回答，执行单项评分或成对比较。适用于证据已完整提供、输出可直接判断的情形；复杂项目若未暴露文件与环境状态，则容易失去关键证据。

输入驱动的判分

Agent-as-a-Judge

Judge 可以先探索 workspace、定位文件、读代码与输出物，必要时从轨迹抽取环境反馈，再对每项 requirement 给出满足 / 不满足和理由。

主动采证 + 判分

Human-as-a-Judge

专家以用户和开发者视角逐项检查项目。更可解释但成本高，且研究发现不同专家对同一项需求也会发生明显分歧。

人工核验 + 讨论

图的技术内核：评判器的区别不仅在于它是否有多个 Agent，而在于它能否主动选择、定位和检查对判定必要的证据。Figure 1 的示例比较了两个创建隐藏文字图像的开发 Agent：不能只看其“任务完成”自述，还应查看 src/visualize.py 与 results/ 的真实产物。Fig.1 p.2；Fig.8 p.17

教学推论（非论文新实验）：如果一个任务的正确性可以由单一确定性测试精确确认，优先保留测试；Agent Judge 的价值出现在跨文件、跨模态、上下文分散或存在多条验收要求的场景，不等于用 Judge 取代所有规则测试。
03 / DATASET · §§2.1–2.2 · PDF p.3; App. E pp.20–22

DevAI：不是单一道题，而是带结构化验收条件的任务包

每个 DevAI 样例至少有三部分：① 自然语言开发请求 query；② 明确且尽量二值化的 requirements，合计 365 条，并包含 prerequisite 依赖；③ 允许主观与模糊表达的 preferences，合计 125 条。论文评判核心依赖需求满足情况，而不是将 125 个偏好直接混入 365 项硬性满足率。§2.2 p.3; App. E.2 p.20

层次结构与用途常见误读
User query完整开发意图，包含文件位置、数据源、需要输出的图表 / 模型或 API。不能把 query 的短文本当成唯一判分对象。
Hard requirement独立、可检查的开发里程碑；每项可以有前置条件。“文件存在”不自动等于功能完整。
Preference更软的体验、鲁棒性或表现偏好；记录但区别于硬条件。不能直接宣称它们被按与硬条件相同的方式量化评分。
Artifacts + trajectory被测 Agent 最终留存的文件、模型、图表，以及适用条件下的行动和环境反馈。工作目录状态与模型的自述不是同一证据。

论文中一个完整样例：语音情绪识别

附录 E.7 的 JSON 任务包含：下载 RAVDESS 数据、在 src/data_loader.py 中完成预处理与 MFCC、在 src/model.py 中实现 CNN–LSTM、存储准确率与混淆矩阵，并用 Flask 提供上传音频接口。七条要求具有显式的 prerequisites，还有噪声处理稳健性、API 易用性两条 Preferences。pp.21–22, App. E.7

数据集有效性的边界：作者为控制开发成本选择相对小规模 AI 项目，并用约束提示要求被测系统在 30 分钟内写入、执行、保存代码；评测环境可能无 GPU。这样的任务不是任意规模生产软件工程的直接代表。§2.2–2.3 p.3; App. E.1 p.20; App. I p.26

06 / HUMAN GOLD STANDARD · §3.2 · PDF pp.4–6

人类评判并非天然 Ground Truth：作者如何建立“共识参考”

三名具有 AI 研发经验的评判者先独立、在指引较少的条件下评分，再就分歧讨论形成共识。原文报告首轮合计 58 小时，共识阶段另耗 28.5 人时，共 86.5 人时。两两评判者之间的分歧约 10%–30%；对共识比较，三人独立多数票的整体错误率降至 6.01%。§§3.1–3.2 pp.5–6; App. H p.25

为什么会分歧？

同一需求可能涉及文件是否真实、代码能否执行、最终产物是否有效、前置条件失效时是否仍可独立打分。不同人对这些边界可能解释不同。

如何验证共识并非完全随意？

作者另招 10 名专家，在随机 7 个 OpenHands 任务上检查；文中报告其多数票与原三人多数票一致率为 97.67%，与原共识结果为 95.23%。规模仍只是 7 个任务的额外检查。

必须区分：Human consensus ≠ 不可错的真实标签。作者承认即使讨论形成共识仍可能出错。因此后文的 Alignment Rate 准确说是“与该人工共识的匹配率”，不能直接译作独立验证的“真实准确率”。§3.2 p.6; App. P p.39

附录 H 的 Figure 11 展示了三位专家事后总结的不同标准：有人主要目测、有人对虚拟数据更严格、有人重点看环境日志。它说明先明确定义评分 Rubric，再校准人类标注是方法论的一部分。p.42 Fig.11

07 / ARCHITECTURE · §4.1 · PDF pp.6–7; App. K p.32

Judge 的“工具”是什么？从 8 个候选模块到有效子集

论文最初设计 8 个模块，但并不是越多越好。Figure 5 和正文给出模块功能；最终依据消融保留更有帮助的组合，使用动态证据而非简单给 Judge 塞入全部代码与全部轨迹。§4.1 pp.6–7; Fig.5

Graph

建立工作区结构图：文件、模块、依赖。

Locate

按需求定位相关目录 / 文件。

Read

读取多模态材料；作者称支持 33 种格式。

Retrieve

从长轨迹抽取与需求相关的执行证据。

Ask

基于具体证据判定 Requirement 满足与否。

Search

代码片段检索；本研究小工作区中会引入噪声。

Planning

规划采证动作；实验中存在不稳定性。

Memory

保存历史判断；错误可能沿需求传播。

准确记录最终组合：正文 §4.1 写明采用 Graph + Locate + Read + Retrieve + Ask 的五模块方案。与此同时，针对 OpenHands 单项消融，在 Ask + Graph + Read + Locate 四项时达到 90.44%，再加入 Retrieve 变为 90.16%；在 GPT-Pilot 上 Retrieve 带来的轨迹证据更有帮助。两种陈述并不冲突：最有用组合取决于被测系统及是否有有效轨迹。p.7 §4.1; p.8 §4.3; App. K p.32–33

Judge Agent 一次判定怎么跑？从需求到可追溯证据

STEP 01读取单项 Requirement

拿到验收条件与前置需求，而非只读整题文本。

STEP 02构建 / 查找证据

Graph 建结构、Locate 找路径、Read 看代码 / 图片。

STEP 03可选取轨迹证据

若有灰盒轨迹，Retrieve 摘取执行反馈或关键报错。

STEP 04Ask 给出判定

SATISFIED / UNSATISFIED + 依据；汇总依赖满足情况。

附录 L 的 System Prompt 要求 Judge 只依据具体项目证据评估需求，并提供理由；Ask Prompt 的输出标签是 <SATISFIED> 或 <UNSATISFIED>。Locate Prompt 把 Requirement 映射到最多 5 个文件路径；Retrieve Prompt 则偏重轨迹中的环境反馈而非重复提取文件内容。App. L pp.34–36

证据能直接支持的判断不能直接推出
文件路径存在目标文件可能被创建。文件内容功能正确、确实执行过。
代码实现某算法或接口是否有实质性逻辑。运行环境稳定、真实数据被加载。
输出图片 / 模型结果产物是否存在且格式 / 内容可见。产物一定由目标流程真实生成。
轨迹中的执行反馈运行时错误、操作路径、最新执行状态。轨迹完整且未经遗漏 / 工具输出可信。
论文不是承诺“每项都重新运行完整项目”。Figure 8 描述 Judge 的检查与证据流程；Appendix N 的失败案例说明即使能读文件仍可能把合成数据误判为真实数据。不要把“工具增强的证据分析”直接等同形式化验证或完整动态测试。Fig.8 p.17; App. N p.38

Black-box 与 Gray-box：评判器究竟能看什么？

Black-box · 无人工整理轨迹

无需获取研究者精心收集的被测 Agent 内部轨迹；仍可检查工作区与产物，因此不等于只读最终自然语言答案。

更贴近一般可获得的数据条件

Gray-box · 补充整理后的轨迹

可读取研究者经过专门插桩与采集的步骤数据，用于核对动作、环境返回和成本；原文提醒这一类轨迹在实践中往往难以取得。

10 / METRICS · §§3–4 · PDF pp.5–8

把四类统计指标拆开：不能拿“90%”回答所有问题

Requirements Met (I / D)

被测开发 Agent 被判定满足的要求比例。I 不考虑依赖；D 结合前置依赖。它回答“开发 Agent 做成多少要求”，不是 Judge 自身准确率。

Task Solve Rate

55 个任务中完整满足全部硬性要求的比例；1.81% 对应 1/55。不是 Requirement 通过率。

Alignment Rate ↑

自动 Judge 的逐条要求判定，与人类共识标签相同的比例，分母是对应要求判断；可因不平衡而虚高。

Judge Shift ↓

同一组被测 Agent 的要求满足率等汇总结果，相对人工共识的绝对偏移；低 Shift 不代表每一条判断都对。

Alignment = （与 Human consensus 一致的 Requirement 判断数）/（比较的 Requirement 判断总数）解释 §4.2 的定义：论文指出该指标覆盖 365 项要求的评判；不同系统与设定单独报告。
Judge Shift = | 自动 Judge 的汇总指标 − Human consensus 的对应汇总指标 |解释表中红色百分数的绝对差，必须保持 I 对 I、D 对 D、Solve 对 Solve。

为什么 Figure 6 要看 PR 曲线？满足要求是少数类；Judge 如果总说“不满足”，即使漏掉大量成功要求，也可能有不错的一致率。Precision–Recall 曲线揭示对“满足”类别的查准与查全权衡。研究在自身实验条件下用它补充 Judge Shift 和 Alignment。§4.2 p.8; Fig.6

不要把论文的“90% 对齐”写成“90% 真实正确率”或“比人类更可靠已经被证明”。比较基准是作者构建的人类共识，且 Figure 6、额外 10 人复核均有具体样本条件。原文说概念验证在部分条件下表现与人工接近，仍列出失败案例。§4.2 p.8; Apps. N/P pp.38–39

Search 没发挥作用：论文是如何排除简单解释的？

附录 K.2 换用 BM25（表格中部分拼写为 BM2.5）、Sentence-BERT 和 Fuzzy Search：分别报告 86.06%、87.70%、85.52%，而不使用 Search 为 90.44%。作者倾向于认为工作区很小、全文可放入上下文，使检索噪声超过其收益；这不是“所有代码库都不该用检索”的证据。p.32 App. K.2

Retrieve 能不能帮助？看场景和截断策略

GPT-Pilot 的附录 K.3 对照：不使用 Retrieve 为 83.88%，使用 Gray-box Retrieve 为 86.61%。轨迹级截断保留尾部信息更重要；作者观察最终状态往往出现在长轨迹后部，而单步日志中的错误信息常在头部、路径信息常在尾部。p.33 Table 7

13 / FAILURE ANALYSIS & LIMITS · Apps. N/O/P pp.38–39

Judge Agent 仍会判断错：两类错误最值得研究

误把合成数据当真数据

Task 40 要求使用 CNN/DailyMail 数据。作者的文字分析称 Judge 因为只查文件路径与内容，被合成数据误导；但同页 Table 9 中此案例的布尔标签写为 Judge=False / Human=True，表格与文字对判定方向存在矛盾。可保留“数据来源核验是难点”这一机制启发，不能把该例的具体正误方向当作已核实事实。App. N p.38

误把“设置参数”当“调参”

Task 46 需要学习率、批大小等进行调优。Judge 检查到参数已设置便判定满足，人类认为缺少“实际调整 / 优化”的关键语义。要求细粒度与证据标准依旧重要。App. N p.38

附录 N 还按任务类别统计失败样本，其中 Data preprocessing / postprocessing 为 10，Dataset / Environment 为 8；这些是论文记录的分类计数，不能误写成按总样本归一化后的错误率。Table 8 p.38

换 Judge 后端是否会改变结果？

附录 O 在指定对照下报告不同后端相对人类共识的 Alignment：Llama 3.2 90B 为 87.76%、Qwen Coder 2.5 32B 为 88.73%、GPT-4o-2024-05-13 为 90.16%、Claude-3.5-Sonnet-20241022 为 92.95%。它说明后端选择可影响 Judge 结果，但仅是论文设置下的敏感性分析，并非当前模型排名。App. O p.39

研究已演示

AI 开发任务上的基于文件、输出物与可选轨迹的细粒度判定；与人类共识对比；组件消融和人工成本估算。

研究没有全面证明

跨行业、跨语言、真实生产负载的稳定表现；Judge 必定检测所有“假数据 / 假执行”；在线生成器—Judge 双向自我改进的可靠收益。

作者自身提出的风险：自动 Judge 错误或偏见可能传播、削弱人的监督。第 6 节关于让 Judge 反馈被 Agent 在线利用、相互改进，属于潜在方向，而非本研究已完成的产品化闭环。§6 p.9; Impact Statement p.9

15 / TAKEAWAYS · ACTIVE RECALL

结论、一页复盘与自测：读完至少带走这六件事

01 评测单元

Task → Requirement → Dependencies；同时区分硬要求与软性偏好。

02 证据来源

Code + files + artifacts；轨迹是可选的额外维度，不是黑盒方案的必需项。

03 评判流程

Graph / Locate / Read / Retrieve / Ask，围绕具体问题动态采集证据。

04 评分口径

I vs D、Requirement vs Task、Shift vs Alignment、PR，各自分母不同。

05 实证结论

在作者实验中，相比文字型 Judge，工具增强的 Agent Judge 对人工共识的匹配水平更高，但收益有条件。

06 方法局限

人工共识非绝对真值；假数据与语义要求可能误判；组件越多不必然越可靠。

自测 1｜DevAI 有 365 个 Requirements，若一个被测系统的 I 满足率为 45%，是否意味着 45% 的完整任务完成？
不能。Requirement Met (I) 统计独立需求的总体满足比例；Task Solve 要求单个任务的全部必需条件成立。论文 GPT-Pilot 的 I 为 44.80%，但完整 Task Solve 仅 1/55（1.81%）。
自测 2｜Agent-as-a-Judge 与人工共识 Alignment 为 90%，是否证明它在每个领域判断的客观正确率都是 90%？
不能。论文中的百分比对应特定系统与黑 / 灰盒条件下，对人工共识的逐项匹配率；人类共识可能仍有误差、样本为 AI 开发任务，不能跨场景泛化。
自测 3｜OpenHands 的四工具版本 90.44%，加入 Retrieve 后 90.16%，能否得出“所有轨迹检索都是负收益”？
不能。这是特定 OpenHands 消融；GPT-Pilot 中加入 gray-box Retrieve 则从 83.88% 提升至 86.61%。是否收益取决于轨迹覆盖、检索噪声与被测系统。
自测 4｜发现目标文件与目标图片就可以认定数据源和功能真实性了吗？
不可以。不能。附录 N 的假 CNN/DailyMail 数据讨论说明仅看文件形态可能遗漏来源问题；但其 Table 9 与文字分析对案例 1 的判定方向不一致，应保留这一原文矛盾。需要额外来源验证、执行证据或确定性检查。
自测 5｜文中的 97.64% 成本节省说明什么，不能说明什么？
该值基于作者假设 15 美元 / 人时，将 86.5 人工评测人时估算为 1297.50 美元，与 Agent Judge API 费用 30.58 美元比较。它是研究成本假设下的估算，非所有生产场景的实际总拥有成本。
