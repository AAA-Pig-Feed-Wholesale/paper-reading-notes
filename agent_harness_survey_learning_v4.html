01｜一句话读懂这篇论文

这篇论文试图把“模型外面那些决定 Agent 能不能可靠工作起来的工程系统”正式抽象成一个独立研究对象：Agent Harness Engineering。

核心判断：当基础模型能力不断增强后，真实 Agent 系统的瓶颈不再只来自模型本身；执行环境、工具接入、上下文管理、生命周期、可观测、验证与治理这些外围机制，会越来越直接决定 Agent 的可靠性、成本、安全性和可维护性。

因此，作者不是再提出一个新的 Agent framework，而是想建立一张“分析 Harness 的统一地图”。ETCLOVG 七层就是这张地图。

02｜作者为什么要写这篇 Survey？

问题 1：概念碎片化

业界已经有 runtime、sandbox、MCP、memory、observability、eval、policy 等大量组件，但缺少一个把它们放在同一体系中讨论的框架。

问题 2：模型视角过强

很多 Agent 研究仍习惯把失败归因于模型能力，却低估了执行环境、上下文、权限、验证等系统因素。

问题 3：实践发展快于理论

大量生产级能力首先出现在开源项目和商业产品里，学术文献中的术语与边界尚未完全统一。

作者的三个主要 Claim

Claim含义应该怎么理解
ConceptualHarness 可能成为 Agent reliability 的 binding constraint。同一个模型，换一套执行、上下文、验证或治理机制，系统表现可能显著不同。
Taxonomic提出 ETCLOVG 七层框架。给 Harness 研究一个统一词汇表，帮助比较不同系统到底“负责哪一层”。
Empirical将 170+ 开源项目映射进 taxonomy。不仅做概念归纳，还尝试用真实生态验证：哪些层已经成熟、哪些仍是空白。

03｜Harness 到底是什么？先把边界讲清楚

这篇文章里的 Harness 不是单指某个 library，也不是 LangGraph、MCP、memory 其中任何一个组件。更接近：

Foundation Model │ ▼ Agent reasoning / action policy │ ▼ ┌─────────────────────────────────────────┐ │ Agent Harness │ │ execution · tools · context · lifecycle │ │ observability · verification · governance│ └─────────────────────────────────────────┘ │ ▼ Real environment / APIs / files / browser / OS
关键边界：Harness 的关注点不是“模型会不会推理”，而是“怎样把模型能力组织成一个可运行、可控制、可验证的 Agent 系统”。

因此，Harness Engineering 天然是一个系统工程问题：它跨 runtime、security、software engineering、evaluation、distributed systems、HCI 等多个方向，而不是模型算法的一个小分支。

04｜作者的历史叙事：Prompt → Context → Harness

阶段 1 · Prompt Engineering

主要优化“如何对模型下指令”。核心对象仍是一次模型调用。

重点：instruction、few-shot、CoT 等。
阶段 2 · Context Engineering

关注“模型当前能看到什么”，开始系统化处理记忆、检索、上下文压缩和状态。

重点：RAG、memory、context window、compaction。
阶段 3 · Harness Engineering

关注“整个 Agent 如何长期、可靠地运行”，把模型嵌入执行、工具、验证、治理等完整系统。

重点：runtime、orchestration、observability、verification、governance。
不要把它理解成严格替代关系。Prompt、Context 仍然存在，只是 Harness 把工程视角进一步向系统外层扩展。作者真正想表达的是研究关注点的扩大。

05｜这篇 Survey 是怎么做的？

论文不只是整理概念，还做了一个面向开源生态的项目映射。理解这一点很重要，因为 ETCLOVG 并非纯粹从抽象理论“演绎”出来，而是带有明显的实践归纳色彩。

文献与概念梳理

作者汇总 Agent 相关研究与工程术语，尝试把大量彼此重叠的概念放进统一层次结构。

开源项目映射

将 170+ 项目按主要能力归入 ETCLOVG，用生态分布观察各层成熟度与空白。

读 Survey 时要保持一个意识：taxonomy 是分析工具，不是自然界唯一正确的分层。很多真实项目天然跨越多个层；作者的分类更像“主要职责归属”。

07｜七层不是七个孤岛：一次 Agent 行动如何穿过它们？

① Lifecycle 决定下一步要做什么 │ ▼ ② Context 组装当前模型可见信息 │ ▼ ③ Tooling 把动作转成标准化工具调用 │ ▼ ④ Execution 在 shell / browser / sandbox 中真正执行 │ ├──────────────► ⑤ Observability 记录 trace / log / metric │ ├──────────────► ⑥ Verification 判断结果是否正确/充分 │ └──────────────► ⑦ Governance 检查权限、策略与审计要求 │ ▼ 回到 Lifecycle 继续循环

这也是为什么论文强调 Harness Engineering 是跨层系统设计。真正的可靠性问题经常不属于某一个单独模块，例如“工具执行错了但没有被发现”同时涉及 Tooling、Execution、Observability 和 Verification。

08｜Structural Core vs Control Plane

论文中一个非常有用的理解方式，是把七层进一步看成两类功能：

Structural Core

E / T / C / L

它们让 Agent “能够行动”：有执行环境、有工具、有上下文、有生命周期和编排。

Control Plane

O / V / G

它们让 Agent “可被管理”：知道它做了什么、判断它做得对不对、限制它能做什么。

这是论文最值得保留的系统观之一：一个 Agent 能跑起来，不等于它已经具备生产级 Harness。生产化的困难往往正集中在 O / V / G。

09｜作者强调的三类跨层权衡

Cost · Quality · Speed

更多检索、更强 verifier、更长轨迹通常提高质量，却也增加 token、延迟和运行成本。Harness 的目标不是单点最优，而是系统级折中。

Capability · Control

给 Agent 更强 shell、browser、filesystem 权限会提升能力，但攻击面和误操作风险同步扩大。

Model · Harness Coupling

Harness 往往隐含对特定模型能力和缺陷的假设；模型升级后，过去有效的 scaffolding 可能变成冗余甚至约束。

这三组矛盾说明：Harness 不是简单“把组件堆得越多越好”。真正的设计问题是哪些控制值得付出复杂度和成本。

10｜170+ 开源项目映射，说明了什么？

作者将大量真实项目映射到七层，试图回答“Agent 工程生态目前发展到了哪里”。最值得关注的并不是具体项目数量，而是成熟度分布的不均衡。

观察论文带来的解释
Lifecycle / Orchestration 非常活跃Agent framework 最早、最明显的需求就是“让模型循环起来、管理状态并编排多步骤任务”，因此这一层工具非常丰富。
Execution / Tooling 已形成较清晰工程形态shell、browser、sandbox、API/tool protocol 等已经出现大量稳定实践。
Verification 正快速成为核心层Agent 从“生成答案”转向“执行任务”之后，仅靠语言质量无法判断任务是否真的完成，因此 verifier/test/eval 重要性上升。
Observability / Governance 相对欠成熟这两层在生产系统里极重要，但部分能力仍集中在商业平台、内部基础设施或安全体系中，开源生态相对分散。
注意：“项目多”不等于“问题已经解决”。开源数量只能说明关注度和工具生态，不能直接证明某层已经形成统一标准。

11｜这篇论文真正的新意在哪里？

新意 1：把 Harness 从“杂项工程”提升为研究对象

过去 execution、memory、eval、security 往往分别讨论；论文试图说明它们其实共同决定 Agent 系统质量。

新意 2：统一语言

ETCLOVG 的价值首先是沟通：看到一个新系统时，可以快速判断它主要创新在哪一层，缺失哪一层。

新意 3：把可靠性问题从模型内部移向系统层

Agent failure 不应自动归因于“模型不够聪明”；错误也可能来自 context 污染、tool schema、sandbox、state recovery 或 verifier。

新意 4：强调控制面

Observability、Verification、Governance 被独立出来，体现 Agent 从 demo 走向 production 后关注点的变化。

12｜这篇论文有哪些局限？

① Taxonomy 是否有唯一性？

没有。七层是作者提出的分析框架，边界存在主观性。例如 memory 既可以视为 Context，也可能涉及 Lifecycle；sandbox 既属于 Execution，也与 Governance 紧密相关。

② 开源项目映射能否代表全部生产实践？

不能。大型公司的 observability、policy、audit、runtime infrastructure 很多并不开源，因此开源分布可能系统性低估某些生产级能力。

③ “Harness 是瓶颈”能否普遍成立？

更准确地说，这是论文提出并用若干现象支持的研究判断，而不是对所有 Agent 任务都已被严格证明的普遍定律。模型能力仍然可能是主要瓶颈。

④ 七层会不会很快变化？

会。Agent 领域迭代很快，协议、memory、sandbox、verification、computer-use 等方向仍在快速演化，因此 taxonomy 更适合作为当前阶段的组织框架，而不是永久标准。

13｜如果你现在去读原文，建议这样读

  1. 先读 Abstract + Introduction：只抓一个问题——为什么作者认为 Harness 值得成为独立研究对象。
  2. 再读 taxonomy 总图：先建立 ETCLOVG 的整体结构，不要一开始陷入项目名和工具名。
  3. 逐层读 E→T→C→L→O→V→G：每层只记三件事：它解决什么、典型机制是什么、与相邻层边界在哪里。
  4. 重点读 cross-cutting synthesis：这里比项目罗列更有研究价值，因为它讨论 cost/control/coupling 这些真正的系统问题。
  5. 最后看 ecosystem mapping：把它当“证据和现状扫描”，而不是把所有项目名称都记住。
  6. 回到 Discussion / Limitations：判断哪些是作者的事实总结，哪些是带方向性的观点。

14｜一页论文笔记

研究对象Agent Harness Engineering：模型/Agent policy 外围、负责把 Agent 变成可运行系统的一整套工程机制。
核心问题现有 Agent 工程能力碎片化，缺乏统一 taxonomy，也容易过度把可靠性问题归因于模型。
核心框架ETCLOVG：Execution、Tooling、Context、Lifecycle & Orchestration、Observability、Verification & Evaluation、Governance & Security。
结构理解E/T/C/L 更像 Structural Core；O/V/G 更像 Control Plane。
经验材料170+ 开源项目映射，用于观察各层生态与成熟度。
关键洞见生产级 Agent 的瓶颈可能从“模型能力”转向“Harness 设计”；可靠性是跨层系统属性。
三类权衡Cost–Quality–Speed；Capability–Control；Model–Harness Coupling。
最重要的保留意见七层不是唯一分类；开源生态不完全代表闭源生产系统；“Harness 成为瓶颈”更像研究命题而非已普遍证明的定律。
