02LangChain：The Anatomy of an Agent Harness

核心定义：Agent = Model + Harness。只要不是模型本身，而是在帮助模型保持状态、执行动作、获取反馈、施加约束的代码与配置，都可以被视为 Harness 的一部分。

2.1 这篇文章的推理方法

它不是先列组件，而是采用一个非常清楚的逆向设计逻辑：

我们希望 Agent 具备某种行为 → 找到模型原生能力缺口 → 在 Harness 中加入对应机制。

Filesystem

解决持久状态、跨 session 工作、超出 context 的中间结果存储问题。LangChain 将它视为最基础的 Harness primitive 之一。

Bash + Code

用通用执行能力替代“为每件事预先设计一个 tool”，让模型动态构造解决方法。

Sandbox

决定模型在哪里运行代码、能够访问什么资源、如何隔离风险，并为并行任务提供可复制环境。

Memory + Search

通过文件、AGENTS.md、Web Search、MCP 等把训练后出现的新知识和历史信息送回 context。

Compaction

应对 context rot：摘要旧上下文、offload 大型 tool output，并通过 progressive disclosure 减少一开始加载的信息。

Planning / Subagents

解决长任务分解与并行；子 Agent 通过 isolated context 避免主上下文被不同子任务相互污染。

2.2 这篇最值得留下的观点

Harness 本质上是“把模型智能变成有效工作的系统”。模型负责 intelligence；Harness 决定这种 intelligence 能看到什么、能做什么、如何持续做、怎样知道自己做对了。

另外一个很重要的观点是：今天的 Harness 很大程度上是 context engineering 的 delivery mechanism。filesystem、memory、search、compaction、skills 看似功能不同，本质上都在解决“有限 context 中什么时候放什么信息”。

2.3 Model–Harness Co-evolution

LangChain 还特别讨论了模型在特定 Harness 中后训练后产生的耦合：工具格式甚至编辑逻辑发生变化，都可能影响模型表现。这意味着 Harness 不是完全可替换的外壳；模型和 Harness 可能共同形成一个行为系统。

03OpenAI：Harness engineering in an agent-first world

实验背景：OpenAI 团队用 Codex 构建一个真实内部产品，所有 application code、tests、CI、docs、observability 与内部 tooling 都由 Codex 写成。文章报告约百万行代码、约 1,500 个 PR，最初由 3 名工程师驱动。

3.1 最大变化：工程师不再主要写代码

文章最重要的不是“Codex 写了多少代码”，而是人的工作发生了层级迁移：

旧工作

设计 → 实现 → Debug → Review → 测试 → 修代码。

新工作

设计 environment、明确 intent、构建 tools、暴露 feedback、编码 invariants，让 Agent 自己完成实现与修复。

团队遇到失败时，问题不再是“怎么让 Codex 再努力一点”，而是：系统缺了什么能力？怎样让这个能力对 Agent 可见，并且可以被机械执行？

3.2 Agent Legibility：这篇文章的中心概念

OpenAI 的核心设计目标是让整个工程系统对 Agent “可读”。如果知识只存在于 Slack、Google Docs 或某个人脑子里，对运行中的 Agent 来说几乎等于不存在。

Repo-local docsVersioned plansArchitecture maps LogsMetricsTracesBrowser stateTest results

因此他们没有把 AGENTS.md 做成超长百科，而是让它成为约百行的“目录”，再将知识组织到结构化 docs/ 中，通过 progressive disclosure 逐步展开。

3.3 Feedback Loop 才是真正的 Harness

Codex 可以访问浏览器、DOM snapshots、screenshots、logs、metrics 和 traces，因此它能够自己复现 bug、实现修复、运行应用、观察结果，再继续调整。长时间运行时，单次任务甚至可以持续数小时。

3.4 Enforce Architecture, Not Every Implementation

文章强调的是“机械化约束边界”，而不是告诉 Agent 每行代码怎样写。依赖方向、schema、structured logging、file size、命名规范等都通过 custom lints 和 structural tests 固化。

对 Agent 而言，好的约束不是减少自主性，而是提供一个可以高速行动而不发生架构漂移的空间。

3.5 Entropy 与 Garbage Collection

完全 Agent-generated 的代码库会复制已有坏模式，因此会不断积累 entropy。OpenAI 最初人工清理“AI slop”，后来把原则编码成规则，并通过周期性后台 Agent 自动发现偏差、打开重构 PR。

这使技术债治理变成一种持续的“垃圾回收”，而不是几个月后一次大型清理。

04Anthropic：Harness design for long-running application development

研究问题：如何让 Claude 在几小时尺度上自主构建完整应用，并且保持产品完整性、设计质量和功能正确性？

4.1 Naive Long-running Agent 为什么会失控

Anthropic 观察到两个典型问题：长任务导致 coherence 下降，以及部分模型临近 context 边界时会出现“context anxiety”——提前收尾、草草完成。

早期 Harness 因此使用 context reset + structured handoff：清空上下文、启动新 Agent，再把上一阶段的状态和下一步任务以结构化 artifact 交过去。

4.2 Planner → Generator → Evaluator

Planner

扩展意图

把 1–4 句简单需求扩成完整产品 spec，但刻意不把实现细节规定死，避免错误设计向下游级联。

Generator

真正构建

按 feature / sprint 实现应用，使用 git，并在交给 QA 前先 self-evaluate。

Evaluator

真实使用验证

借助 Playwright MCP 操作真实运行中的应用，检查 UI、API、数据库状态，并依据 testable contract 提交具体 bug。

4.3 Evaluator 的真正意义

Evaluator 不是简单的 LLM Judge，而是能够真正运行应用的 QA Agent。它检查的是“产品是否真的可用”，不是“代码看起来是否合理”。

这揭示了 Harness 的重要设计原则：Verification 应尽量接近目标环境，而不是停留在生成文本本身。

4.4 最重要的新结论：Model 变强后，要删 Harness

当模型从 Opus 4.5 升级到 4.6，一些原本关键的机制变得不再 load-bearing。比如更强模型能持续更长时间工作，于是原本的 sprint decomposition 和部分中间 evaluator 开销可以减少。

Harness 不是越复杂越好。每次模型升级后，都应该重新检查哪些 scaffold 已经失去作用，并把它们删除。

文章给出的判断非常精确：Evaluator 是否值得使用，取决于任务位于模型可靠能力边界的哪一侧。模型自己已经稳定能做的工作，再加 evaluator 可能只是额外成本；接近能力边缘时，Evaluator 才真正提供 lift。

4.5 一个真实成本例子

文章后续更新版 Harness 构建浏览器 DAW 的一次运行约持续 3 小时 50 分钟，token 成本约 124.70 美元。它说明 long-horizon autonomy 在 2026 年已经可行，但仍然是明显的工程与成本权衡，而不是“无限免费自治”。

05三家共同结论：真正稳定的共识是什么？

① 环境比 Prompt 更重要

高能力 Agent 的性能越来越取决于它能进入什么环境、拿到什么工具、看到什么反馈。

② Context 是稀缺资源

不是“给得越多越好”，而是要 progressive disclosure、compaction、offloading 和结构化知识。

③ Verification 必须闭环

tests、browser、logs、metrics、QA Agent 都是在把“生成”变成“生成—观察—修正”的闭环。

④ Harness 与模型共同决定能力

同一个模型换 Harness 可能有显著表现差异；反过来模型升级也会使旧 Harness 失效。

⑤ 长任务依赖外部状态

filesystem、git、structured artifacts、plans 等承担了单个 context window 无法持久保存的工作状态。

⑥ 人类角色向控制层迁移

人的高价值工作从逐行实现转向目标设定、环境设计、约束编码、验收和系统治理。

07Harness 如何随模型能力演化？

模型能力弱

需要更多 planning、task decomposition、context reset、严格 workflow 和多轮 verification 来补足能力。

模型能力增强

部分 scaffold 失去 load-bearing 作用；更简单的 loop 可能就能完成过去必须分阶段完成的任务。

任务复杂度继续提升

开发者不会停下来，而是把 Harness 的能力边界继续向外推：更复杂环境、更长任务、更真实 QA、更高自治。

因此 Harness Engineering 不是“修补模型缺陷”的临时职业。模型越强，人们越可能给它更复杂的任务，于是 Harness 的研究空间会迁移，而不是简单消失。

09读工业界文章时要保留的判断

不是学术 Benchmark

三篇都非常有工程价值，但 OpenAI/Anthropic 的结果主要来自特定内部环境、特定模型与特定任务，不等同于跨场景普遍因果结论。

供应商天然偏向自身技术栈

OpenAI 围绕 Codex、Anthropic 围绕 Claude、LangChain 围绕自己的 agent tooling。应吸收设计思想，而不是机械复制产品选择。

Harness 的“正确答案”不存在

同一种结构在不同模型能力边界下可能从关键组件变成冗余开销。

复杂度必须由失败模式驱动

真正好的 Harness 不是功能最多，而是每个组件都对应一个可以观察到的失败模式或生产需求。

10三篇读完，应该真正留下的 10 条理解

01

Harness 是模型智能与现实工作之间的工程转换层。

02

设计 Harness 的起点应该是“模型在哪种行为上失败”，而不是先堆框架。

03

Filesystem 是非常基础但经常被低估的 Agent primitive。

04

真正有效的 context engineering 依赖结构化、渐进式的信息暴露。

05

Agent 的能力很大程度来自它能否观察自己行动后的真实结果。

06

生产环境需要把“正确做法”编码成可机械检查的约束。

07

长时自主任务必须解决状态持久化、上下文退化和终止判断。

08

Evaluator 的价值取决于任务是否超过当前模型的可靠边界。

09

模型升级后应重新审计 Harness，删除失去作用的 scaffold。

10

Harness Engineering 的终点不是更复杂，而是用最合适的系统结构释放当前模型的能力。
