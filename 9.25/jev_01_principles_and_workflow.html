Jev 原理与 Workflow Evals

基于 TypeSafe 官方《Introducing System One Models & Jev》与 Workflow Evals，重点理解 Jev 为什么被设计成“决策模型”而不是“文本生成模型”，以及它如何被嵌入代码工作流。

资料日期：2026-09｜页面内容区分 原文事实 解释 边界/谨慎点

学习目标

01
说清 Jev 是什么

理解 System One Model、typed probabilistic decision，而不是把它误解成“小型聊天模型”。

02
理解核心机制

理解 Noul / Choice / Score、Calibration、RLCD、Parallel Sampling 的角色与边界。

03
理解 Workflow 思想

知道为什么 TypeSafe 强调“窄问题 + 代码规则”而不是“一次 Prompt 解决整个任务”。

先记一句：TypeSafe 对 Jev 的核心描述是：“unstructured state in, typed probabilistic decisions out”。也就是输入可以是复杂非结构化状态，但输出空间必须事先定义，并附带概率/置信信息。

1. 为什么会有 Jev：TypeSafe 认为“聊天模型 ≠ 自动化模型”

TypeSafe 的问题意识不是“LLM 不够聪明”，而是：当前 LLM 的接口形态更适合与人交互，不一定适合被软件直接依赖。 原文事实

传统 LLM 的默认范式

输入→自回归生成字符串→解析/校验→软件动作

字符串很灵活，但软件要使用它，通常还要做 parsing、schema validation、retry、fallback。

Jev 的目标范式

State→Typed Decision→Code Branch

可能输出什么，在调用前已经定义。模型负责“模糊判断”，程序负责“确定执行”。

解释：这并不是说“生成式 LLM 不适合 Agent”。更准确地说，TypeSafe 想把 Agent/业务系统里大量 classify / route / score / verify / branch 类型的判断，从文本生成问题重新建模成机器可直接消费的决策问题。 解释

2. System One Model：官方想定义一个新的模型接口

维度传统 LLM（官方对照）System One + Jev（官方对照）
训练目标RLHF / RLVR 等RLCD：Reinforcement Learning for Calibrated Decisions
主要输出字符串 / generated text预定义类型的结构化值
采样token-by-token 顺序生成官方称为并行输出
不确定性Prompt 出来的“confidence”可能不稳定每个答案携带概率与 confidence
典型角色聊天、写作、代码、开放式推理classify、route、score、branch、verify
不要过度解读：官方提到“new model architecture”，但当前公开文章没有给出足够细节让外部读者重建 Jev 的底层网络结构；所以本页不会猜测它是不是某种 Transformer 变体、判别式头、能量模型等。 公开边界

“System One”这个名字意味着什么？

TypeSafe 明确说名称受到 Kahneman《Thinking, Fast and Slow》里 System 1 / System 2 区分的启发：System One 强调快速、直觉式判断。它不是在宣称 Jev 复刻了人类认知结构，而是借这个比喻强调“快速决策”定位。 原文事实

3. 三类决策 Primitive：Noul / Choice / Score

Workflow Evals 明确把智能判断拆成三种类型，再由普通程序规则组合。 原文事实

Noul

Yes / No 类型问题，模型返回概率。

“这次工具调用是否越权？”
→ P(Yes), P(No)

适合：guardrail、是否升级人工、是否满足条件。

Choice

从预定义集合中选一项，同时返回分布与 confidence。

intent ∈ {
  refund,
  logistics,
  complaint
}

适合：intent、model routing、tool family routing。

Score

在给定尺度上评分，并给出水平分布和 confidence。

risk_score ∈ [1,5]

适合：风险、优先级、质量、紧迫程度。

关键差异：Structured Output 解决的是“LLM 最终能不能吐出合法 JSON”；Jev 的产品主张更进一步：输出空间本身就是模型接口的一部分，模型不是先生成任意文本再被 JSON 约束。 但“底层到底如何保证这些类型”属于未完全公开实现细节。 解释 + 边界

4. Calibration 与 RLCD：Jev 为什么一直强调“概率”

4.1 Calibration 到底在解决什么

如果一个模型在大量相似样本上给出约 0.9 的置信度，那么理想的校准意味着：这些样本中大约 90% 最终应该判断正确。这里关注的是“置信度数值是否具有统计含义”，而不是单次回答有没有自信语气。 解释

普通 confidence 话术
“我有 95% 把握。”——这可能只是模型生成出来的文本。
校准概率
0.95 应当在经验统计上对应接近 95% 的正确频率。
为什么重要
软件才能据此设置阈值：高置信度自动执行，中等置信度升级强模型，低置信度请求人工或澄清。

4.2 RLCD：官方公开到了哪一步

TypeSafe 把其训练方法命名为 Reinforcement Learning for Calibrated Decisions (RLCD)，并称其优化目标是让模型在 System One 类任务上输出“epistemically honest probabilities”。 原文事实

但目前不能再往下脑补：官方公开文没有完整给出 RLCD 的 reward 形式、优化算法、训练数据配方、校准损失、训练阶段细节。因此可以理解“训练目标”，但不能把 RLCD 当成一套已经公开可复现的方法论文。 公开边界

4.3 为什么 Calibration 很适合自动化

if confidence >= 0.95:
    execute_automatically()
elif confidence >= 0.70:
    escalate_to_stronger_model()
else:
    ask_for_human_review()

这段伪代码体现 Jev 的核心工程价值：不确定性被显式变成控制流的一部分。 解释

5. Parallel Sampling：为什么官方称它比自回归更适合决策

Autoregressive LLM

token₁ → token₂ → token₃ → ... → tokenₙ

输出长度越长，生成步骤越多；后一个 token 依赖前面 token。

Jev（官方描述）

state + questions
        ↓
all decision outputs in parallel

官方称多个结构化决策可以在一次查询中并行产生，而不是逐 token 生成完整字符串。

理解重点：对“选 A/B/C、给 0~5 分、判断 Yes/No”这类任务，输出空间本来就小。如果仍要求模型先写一长串自然语言再解析，可能是一种接口层面的浪费。Jev 的设计就是直接针对“小输出空间、高频决策”优化。 解释

官方还披露：Jev 的 Choice cardinality 当前支持到 255；更高基数的选择可采用先独立评分、再显式选择的两阶段方案。 原文事实

6. Workflow Evals：比单模型 Benchmark 更值得看的地方

TypeSafe 没有只做“给模型一道分类题看 accuracy”，而是构造完整代码 Workflow：所有模型使用同一个工作流，比较在同一 compute graph 下完成自动化任务的效果、成本与时间。 原文事实

6.1 核心方法：Decompose the work, build a harness

复杂业务政策→ 拆成窄问题→ Noul / Choice / Score→ 代码组合→ 最终 Action

TypeSafe 的 Workflow Evals 明确主张：能用代码确定的事情交给代码，需要语义判断的部分才交给模型。 同一套 policy，如果整个压成一个 Prompt，官方测试中平均效果更差、成本更高、速度更慢。 原文事实

6.2 Expense Claim 玩具例子

业务政策：有收据；判断费用类别；餐饮超过 $75 且描述与收据不清晰时需要经理签字；其他情况批准。

Receipt readable?→Expense type?→Description matches?→金额比较（代码）→Approve / Sign-off

这说明 Jev 的理想使用方式不是“替代整个业务程序”，而是变成工作流里的 fuzzy decision node。

6.3 评测参考值如何得到？

Workflow Evals 不是传统 ground-truth 标签体系。官方说明：假设 Harness/Compute Graph 正确，然后把 GPT-6 Astra 与 Claude Fable 5.1（高 thinking）在同一问题上的回答平均，作为 reference probabilities；其他模型使用各 provider 默认 reasoning 设置进行比较。 原文事实

这非常重要：因此“accuracy”更接近“与该参考共识的一致程度”，不是独立客观真值。官方自己也承认，这会让 reference 对 OpenAI / Anthropic 的模型分布存在偏置。 评测边界

7. 四类真实 Workflow：Jev 被放在哪里

Security Incidents

读取告警、资产、授权、维护记录等，先判断是否未授权、是否有解释、证据强度，再由代码决定关闭、排队或 containment。

启发：语义判断 + 硬规则 + 风险级别组合。

Agent Trace Observability

读取 Agent 指令、完整对话、tool calls、最终消息、用户反馈，判断不可逆操作是否越权、任务是否完成、用户是否满意，再决定 auto-close / review / page on-call。

启发：Jev 也能作为 Trace 级判定器。

Invoice Processing

合同、采购单、发票、交付、审批等大量状态进入工作流。求和、日期、账户号、状态等由代码计算；语义性判断由模型回答。

启发：把“算得准”与“理解得准”分开。

Customer Service

先并行读取 intent、frustration、urgency、fraud/legal/person request 等信号，再在必要时做 follow-up questions，最后按安全→事实核验→handoff→close→issue 的顺序执行规则。

启发：多独立判断 + 条件触发 + 优先级规则。

你应该从这四个例子里学到的不是领域知识，而是一个统一 Pattern：
复杂任务 ≠ 一个超长 Prompt。复杂任务 = 多个小的概率判断 + deterministic code + 明确的 branch order。 解释

8. 如何正确阅读官方性能主张

官方主张应该怎么理解不能怎么说
193.6× faster / 444.6× cheaper来自官方四个 Workflow 的汇总结果；官方自己称这可能是实际收益的高端区间。“Jev 在所有任务都快 193×、便宜 444×。”
Zero Hallucinations其核心依据是输出 schema/type 空间受约束，因此不会生成 schema 外的字符串或类型错误。“Jev 的语义判断永远不会错。”
0% type errors这是接口/类型层的保证；官方明确把这和普通 LLM 可能输出非法 schema 做对比。“0% type error = 0% decision error。”
Calibrated confidence官方训练目标强调 calibrated decisions，并提供概率/置信度。在没有独立大规模验证前，直接把官方 calibration 结论泛化到所有领域。
更聪明 / frontier-level on System One tasks只应限定在官方定义的 System One-shaped tasks 与其展示的评测设置。“Jev 是通用能力上等价于 frontier LLM 的模型。”
类型安全解决“输出是否合法”；校准解决“系统是否知道自己可能错”；业务正确性仍然需要任务设计、数据、阈值和外部验证共同保证。

面向下一篇（Jev × Agent Systems）的连接点：一旦模型能直接输出“带概率的 typed decision”，它就很自然地可以放到 Agent Harness 里的 intent routing、model routing、tool gating、verification，以及 Agent Eval 中的 judge 节点。

自测：确认你不是只记住名词

Q1：Jev 和“LLM + JSON Mode”最根本的产品定位差异是什么？
Jev 把预定义 typed decision 当作原生模型接口与训练目标的一部分；JSON Mode 仍通常是生成式 LLM 在字符串生成范式上施加结构约束。底层实现细节则不能在公开资料之外继续推断。
Q2：为什么 calibrated probability 对 Agent 自动化比“模型自报 95% 信心”更重要？
因为前者目标是让置信度具有统计意义，软件才能据此设置执行/升级/人工阈值；后者可能只是自然语言生成结果。
Q3：Workflow Evals 为什么强调 decomposition？
复杂任务被拆成多个独立窄判断，确定性运算和规则留给代码，模型只处理语义性判断；这样更容易控制、调试、复用概率并形成稳定分支。
Q4：“Zero hallucinations”能不能理解为“Jev 不会判断错”？
不能。官方主要把该主张建立在 type/schema 空间受约束、不会输出类型之外内容上。语义判断仍可能错误。
Q5：RLCD 现在能不能按论文级别复现？
不能。官方公开了名称和目标方向，但没有公开完整数学目标、reward 设计、优化算法和训练 recipe。
