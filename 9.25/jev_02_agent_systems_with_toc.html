Jev × Agent Systems

Harness 与 Evaluation：Jev 进入 Agent 系统之后，究竟在做什么？

本页基于 LangChain 官方两篇文章：Building a Harness with Jev 与 Jev-as-a-Judge for Agent Evals。重点不是重复 Jev 的基础定义，而是理解它进入 Agent 系统之后， 如何同时承担运行时决策与运行后评测两类职责。

核心主线： 生成式 LLM 负责开放式理解、推理与生成；Jev 负责边界清晰、需要概率判断的窄决策； 确定性代码负责必须严格执行的规则。把这三类能力分开，是理解 Jev 在 Harness 中价值的关键。

01 · 总体定位

Jev 进入 Agent 后，不是“替代主模型”，而是切出一层 Decision Layer

LangChain 对 Jev 的定位很清晰：它不是通用 LLM 的直接替代品。Agent 仍然需要生成式模型完成开放式推理、文本生成、 复杂解释与上下文理解；Jev 更适合接管其中那些可以被写成有限判断问题的步骤。

User / Environment
输入与外部状态
→
Generative LLM
理解、推理、生成候选动作
→
Jev Decision Layer
选择、评分、是否允许
→
Deterministic Code
真正执行流程与约束
理解 Jev 的最好方式：不是“一个更便宜的小模型”，而是把 Agent Loop 中原本需要再次调用通用 LLM 的某些 classification / routing / gating / judging 决策，抽离成专门的、结构化的概率判断。
开放式能力

Generative LLM

写回答、做复杂推理、总结、解释、生成计划、生成工具参数。

概率决策

Jev

Choice / Score / Noul，处理“选哪个”“质量如何”“是否成立”这类窄而模糊的语义判断。

硬约束

Deterministic Code

权限、Schema、金额上限、白名单、事务、必须执行的安全规则。

来源依据：LangChain 在 Harness 文章中明确把 Jev 描述为对主 Agent 模型的补充，而非 drop-in replacement； 它适合承担大量当前由 LLM 完成的分类/结构化判断任务。
02 · Jev in Harness

为什么 Harness 特别适合放 Jev？

一个典型 Agent Loop 会不断发生“小决策”：该用哪个模型、某个动作危险不危险、是否需要升级、是否继续重试…… 如果每个决策都重新调用一个完整生成式 LLM，系统会付出额外的延迟、成本与输出不稳定性。

传统做法

Agent state
   ↓
Prompt 一个通用 LLM
   ↓
让模型生成 JSON / 文本结论
   ↓
解析
   ↓
执行下一步

问题：每次判断都要经历自回归生成；还需要处理输出格式、解析、随机性。

Jev 型做法

Agent state
   ↓
Typed question
   ↓
Jev
   ↓
typed answer + probability
   ↓
代码按阈值 / 规则执行

目标：让“判断”本身直接成为软件可消费的结构化信号。

LangChain 集成暴露了什么？

官方文章介绍的集成入口是 TypeSafeClassifier。调用时传入 state 与若干问题， 得到分类结果而不是聊天文本。文章指出 state 可以是文本、结构化数据或 LangChain messages， 因而可以直接嵌入 node、middleware hook 或 tool 周围。 

# 概念化伪代码：强调位置，不复刻原文实现
state = current_agent_context

decision = jev.invoke(
    state=state,
    question="当前请求是否需要立即升级处理？"
)

if decision.probability >= threshold:
    escalate()
else:
    continue_agent_loop()
关键不是 API 名字，而是架构位置： Jev 处于“语义状态 → 可执行控制流”之间，把模糊语义转换成概率化、可阈值化的控制信号。
03 · Model Routing

用 Jev 选择模型：把“哪一个模型够用”变成显式决策

LangChain 的第一类示例是 Model Routing。不同请求并不需要同样昂贵、同样强的模型： 简单抽取、直接查找可以进入快模型；架构设计、高风险判断可以进入更强模型。

Latest User Message
当前请求
→
Jev Choice
fast / powerful
→
Selected Model
本次 run 使用

这和传统 Intent Classification 有什么不同？

问题传统 IntentModel Routing
回答什么？“用户想做什么”“哪个模型足够完成这件事”
典型标签退款 / 查询 / 投诉fast / strong / specialist
优化目标意图识别准确质量 × 成本 × 延迟
Jev 作用可做 Choice可根据 criteria 做 Choice，并保留概率与 confidence
LangChain 文章指出，Model Router 的概率与 confidence 可以保留在 Agent state 中。 这很重要，因为 Router 不必只输出“一个标签”，后续 Harness 还可以利用置信度继续做 fallback、审计或二级路由。

更完整的工程化写法

Jev says:
  fast_model      0.72
  powerful_model  0.28

Harness policy:
  p(fast) ≥ 0.85  → 直接走 fast
  0.55 ~ 0.85     → 二级判断 / 小型 LLM router
  < 0.55           → powerful / fallback

上述阈值分层是学习上的工程扩展，不是 LangChain 原文规定的固定阈值。

04 · Tool Risk Gating

Jev 不只决定“去哪”，还可以决定“能不能执行”

LangChain 的第二个 Harness 示例是 Auto Mode：在工具真正执行之前，用 Jev 判断 proposed tool call 是否具有风险，必要时直接阻断。文章特别以 bash 类工具作为示例。

LLM proposes tool call
准备调用工具
→
Jev risk check
危险吗？
→
Policy
Allow / Block / Escalate
→
Tool executes
仅在通过后
⚠
不要把 Jev 当成“万能安全层”。
对于确定性的硬规则，例如禁止写生产数据库、禁止访问某路径、金额不得超过上限，优先使用 deterministic policy。 Jev 更适合那些“危险性依赖语义与上下文”的灰区判断。

一个实用的三层 Guardrail

Layer 1

Hard Rule

白名单、权限、Schema、命令黑名单。能确定性判断就不要交给模型。

Layer 2

Jev Semantic Gate

判断“这个 bash 调用在当前任务里是否合理”“是否有潜在破坏性”。

Layer 3

Human Approval

高风险、低置信度、不可逆动作进入人工确认。

来源依据：LangChain 的 AutoModeMiddleware 示例明确在工具执行前用 Jev 检查 risky decisions，并可阻止调用。
05 · Jev-as-a-Judge

同一个 Decision Model，为什么又能做 Agent Evaluator？

因为很多 Agent Evaluation 本质也是一个决策问题：给定 Agent 的输入、执行轨迹、输出与证据， 判断“是否通过”“质量是多少”“更接近哪种失败类型”。

Noul

二元判断

“最终答案是否由检索证据支持？” → 返回成立概率。

Score

有序评分

“答案有多有用？” → 对有序 rubric 给出概率与 confidence。

Choice

类别选择

“该 run 属于合理搜索、无必要搜索还是未搜索？” → 返回选项概率。

Harness 阶段：Jev 判断“下一步该怎么做”。
Eval 阶段：Jev 判断“刚才做得怎么样”。

为什么 LangChain 会把它视为“第三类 evaluator”？

Evaluator优势主要短板典型任务
Code-based 快、便宜、确定性强 难处理开放式语义 是否调用工具、Schema、执行结果、硬规则
LLM-as-a-Judge 能读懂开放式轨迹和复杂 rubric 慢、贵、非确定、需要校准 帮助性、完整性、开放式质量判断
Jev-as-a-Judge 面向结构化决策，返回 typed answer + probability 尚属早期；适用边界需更多任务验证 边界较清晰的语义性判定、Score、Choice

连续 quality score：稳定性

LangChain 用相同输入重复评估，观察 quality score 的方差。Jev 的平均单样本方差为 0.0000149；文章报告 Luna 的方差约为其 433×、Terra 913×、Claude 92×。

最重要的统计解释：低方差 ≠ 高准确率。一个 Judge 完全可能“稳定地判断错”。 LangChain 自己也明确区分 accuracy（与人工 oracle 一致）和 variance（相同输入能否给出稳定判断）。

07 · Evaluator 选择

Jev-as-a-Judge 并不是把 Code 和 LLM Judge 全部替掉

更合理的理解是三者分别覆盖不同区域：

评测问题优先工具原因
Tool 参数是否合法？Code确定性规则，不需要模型
是否调用了必须调用的工具？CodeTrace 中可直接验证
回答是否有明确证据支撑？Jev / LLM Judge需要语义判断；若 rubric 边界清晰可尝试 Jev
回答“好不好”，需要长解释与复杂权衡？LLM Judge / Human更开放、更主观
是否属于某类失败模式？Jev Choice有限类别 + 语义判断
高风险争议样本Human自动 Judge 不应作为唯一责任主体
一个成熟 Eval Stack 往往不是“选择一个 Judge”，而是组合： Code 做硬检查 → Jev 做窄语义判定 → LLM/Human 处理复杂与争议样本。
08 · 统一视角

最值得记住的：Jev 在 Agent 中有两种时间位置

Runtime

执行前 / 执行中

问题：下一步该怎么做？

  • 选 fast 还是 powerful model
  • 某个 tool call 是否危险
  • 是否升级人工
  • 是否继续 / 重试

角色：Harness Decision Layer

Post-run / Async

执行后

问题：刚才做得怎么样？

  • 任务是否通过
  • 质量得分如何
  • 失败属于哪一类
  • 线上 trace 是否需要告警

角色：Evaluator / Judge

Agent State
→
Jev Runtime Decision
route / gate
→
Action & Tool
→
Trace / Outcome
→
Jev Eval Decision
pass / score / class

这意味着 Jev 并不是某个单独 Harness 模块，而更像一种可以被复用的 decision primitive：凡是系统中存在“语义模糊、但输出空间有限”的节点，都可能成为候选位置。

09 · 使用边界

什么时候应该想到 Jev，什么时候不应该？

场景是否适合 Jev理由
Intent / Skill / Model Routing适合有限 Choice，且需要语义判断
Tool Risk Gating适合做补充语义风险可用 Noul；硬规则仍应代码兜底
Pass / Fail Eval适合候选可将 rubric 拆成多个原子二元判断
Failure Type Classification适合有限类别 Choice
长文本总结 / 写作不适合Jev 不生成开放式文本
复杂开放式推理不适合替代 LLM需要生成中间内容与自由表达
确定性权限规则通常不需要代码更可靠、更可审计
高风险最终裁决不应单独承担应配合硬规则与人工责任链

可以用一个判断公式记忆

如果问题同时满足： ① 输入是非结构化/语义状态；② 输出空间有限；③ 需要概率或置信度；④ 判断会高频发生； 那么 Jev 就很值得考虑。
如果问题本质是“生成”“开放式推理”或“确定性规则”，优先考虑 LLM 或代码。
10 · 复盘

读完这两篇 LangChain 文章，应该形成的 8 个结论

  1. Jev 不负责“把 Agent 变聪明”，而负责把 Agent 中一部分决策变成更直接的软件信号。
  2. Model Routing 是典型 Choice：让不同复杂度请求进入不同模型。
  3. Tool Risk Gating 是典型 Noul：在工具执行前判断动作是否危险。
  4. Jev 的 probability / confidence 可以被 Harness 用于 threshold、fallback、升级与审计，而不是只取一个标签。
  5. Agent Evaluation 本身也是 decision problem，因此 Jev 可以成为 Code 与 LLM Judge 之外的第三类 evaluator 候选。
  6. LangChain 的天气 Agent 实验显示 Jev 在该窄设置下表现出很高的一致性、很低的 score variance，以及较低的 latency / cost。
  7. 稳定 ≠ 正确。即便 variance 很低，也必须用人工标注或可信 oracle 验证 alignment。
  8. 最合理的系统不是 “LLM vs Jev vs Code 三选一”，而是让三者各做最擅长的部分。
思考题 1：为什么 Tool Risk Gating 不能完全替代 hard-coded policy？
因为某些安全规则有明确、不可协商的边界，应该由确定性机制强制执行。 Jev 更适合补充上下文相关、语义性的灰区风险判断，而不是成为唯一的安全防线。
思考题 2：为什么 Jev-as-a-Judge 的低方差值得关注，但不能单独证明它是更好的 Judge？
方差衡量重复判断是否稳定；更好的 Judge 还需要与人工/真实标准对齐。 一个模型可以始终给出同一个错误答案，因此必须同时看 accuracy/alignment 与 variance。
思考题 3：Jev 最适合接管 Agent Loop 中什么类型的节点？
输入含有语义不确定性，但输出空间有限且可以写成 Choice / Score / Noul 的节点， 例如路由、风险判断、升级、是否通过、失败分类等。
