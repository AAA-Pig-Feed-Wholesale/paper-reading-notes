Harness Engineering
11 个 Coding Agent 的源码解剖

《Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems》精读笔记。重点不是“再讲一遍 Harness 是什么”，而是理解作者如何从真实生产源码中抽取结构、模式与演化趋势。

Paul Barbaste · Tristan Darrigol · Germain Vu · Tom Wiltberger arXiv:2609.00006 83 pages · 7 figures · 18 tables 11 harnesses + 1 meta-harness ≈ 4M lines of source code

01这篇论文到底在研究什么？

作者先提出一个极其直接的定义：Agent = Model + Harness。模型提供“智能”，Harness 则负责把这种智能变成真实世界中的持续行动：循环、工具、上下文、安全、编排和扩展接口。

这篇论文的真正贡献，不是再给 Harness 下一个定义，而是第一次大规模地问：生产环境中的 Harness 到底是怎么写出来的？
不是 Benchmark

不比较谁分高

作者明确说：本文“不 benchmark、不排名”。它关心的是架构，而不是 SWE-Bench 排名。

源码实证

直接读生产代码

研究对象覆盖约 400 万行 Python、TypeScript、Rust 源码，重点观察 loop、tool、memory、permission 等真实实现。

纵向演化

还看 90 天怎么变

原先 8 个系统在 4 月已经分析过，7 月再次固定版本并做源码 diff，因此可以观察模式如何扩散、模仿和迁移。

阅读关键词：这不是“Agent 算法论文”，更接近一篇 software architecture empirical study。它想做的是 Harness 领域的“reference anatomy”。

作者选择 11 个 Harness，刻意覆盖三条轴线：设计哲学、成熟度、市场位置。同时加入 Omnigent 作为 meta-harness 对照。

03七个 Canonical Subsystems

这篇论文的七层和上一篇 ETCLOVG 不完全相同。它更偏 Coding Harness 的“内部器官”，围绕实际源码结构来拆。

1. Agent Loop

负责“推理 → 行动 → 观察 → 再推理”的主循环，也拥有停止条件、错误恢复、并发执行等控制。最小形态是 Mini-SWE-Agent 的线性 while；最大形态可到 OpenHands 的 event-sourced conversation engine。

2. LLM Integration

不仅是“调 API”。它还包括 provider protocol、prompt assembly、cache、thinking、routing、model-family differentiation。论文强调：生产 Harness 正在越来越深地与模型族共设计。

3. Tools & Actions

决定 Agent 能做什么，尤其是读写文件、命令执行和编辑。论文观察到工具数从 bash-only 到数十个 typed tools；当工具过多时，deferred loading 开始成为重要模式。

4. Memory & Context

核心任务是“如何花掉上下文窗口”。包括线性 history、summary/compaction、跨会话 memory、层级 Markdown context、JIT retrieval 等。

5. Safety & Permissions

决定什么可以直接执行、什么要询问用户、什么必须禁止。系统之间分歧极大：从只有 step/cost limit，到 policy-as-code + LLM reviewer + OS sandbox。

6. Orchestration

负责 sub-agent spawn、context fork、worker coordination 和跨 agent 连接。作者特别指出：生产系统的多 Agent 往往更多用于“并行探索”，而不是并行写代码。

7. Extensibility

用户如何把能力装进 Harness：config、hooks、skills、plugins、MCP、ACP。2026 年最显著变化之一，就是这一层从“辅助功能”变成平台化的核心。

论文还指出两条跨层 surface：Interface layer（CLI/TUI/IDE/HTTP/SDK）与 Session substrate（resume/fork/transcript/persistence）。它们不被单独算作七层，但会穿透多个 subsystem。

0411 个系统：不要逐个背，而要看“设计立场”

Claude Code强 provider coupling；大量 typed tools；递归 sub-agent；Skills/MCP/hooks；缓存边界和权限体系都很成熟。
Codex CLIRust 大型工程；模型目录由服务端下发；多层 permission + native sandbox；更像一套可持续升级的平台 runtime。
Gemini CLI异步生成器 loop；分层 memory；跨平台 sandbox；同时支持 A2A，协议化程度高。
Mistral Vibemiddleware-pipeline 很有代表性；provider-first + generic fallback；权限 scope 与 hooks 结构清晰。
OpenHandsevent-sourced；conversation tree；外层 judge；还能把 rival harness 当 backend host。
Aider单 Agent、编辑策略丰富；保留“工具简洁但 edit contract 深”的老派路线。
Mini-SWE-Agent证明“把事做完”的最低 Harness 很小：简单 loop + bash + history + limits。
HermesSkill 自生成、自修正、跨会话 memory、swarm，是“自进化 Harness”方向的代表。
Pi极小 core + 极强 extension host，把很多能力搬到 event bus 上，是“minimal core”极端路线。
OpenCode强 client/server 架构，HTTP/OpenAPI/SDK，多 UI 都只是客户端，平台化最直观。
OpenClaw多渠道 gateway，证明 Harness 思路已扩展到非纯软件工程场景。
Omnigent（对照）不是 Harness，而是 meta-harness：把 Claude Code、Codex 等当成 interchangeable components。

0529 个设计模式：论文真正“值钱”的部分

作者不是只列 feature，而是把跨系统反复出现的结构抽象为 recurring patterns。下面这些尤其值得理解：

怎么理解这些 pattern？

不要把它们当成“29 个名词”。它们描述的是：当 Agent 从 Demo 走向长期运行，工程问题会重复出现，而不同团队会独立收敛到相似结构。比如：

Context Forking

sub-agent 不应该直接污染主 Agent 的完整上下文，因此会克隆父状态、形成隔离分支，再返回摘要或结果。

Outer Verification Loop

仅靠 Agent 自己说“完成了”不可靠，于是 Harness 在主 loop 之外再加 judge / stop guard，对终止条件进行二次验证。

Lineage Compaction

压缩不再只是“把旧对话总结一下”，而是保留 session ancestry，让压缩后的上下文仍可追溯前序状态。

Client/Server Harness

Agent runtime 变成服务端，TUI、Web、IDE、CI 都只是 client。这是“工具 → 平台”的直接证据。

06论文最出圈的发现：两个“缺席”

0 / 11

没有通用 Agent Framework

作者检查 LangChain、LangGraph、AutoGen、CrewAI、Pydantic AI、Semantic Kernel、Google ADK 等大量依赖，在生产 Agent runtime 的主路径中全部缺席。

实际情况：大家普遍使用宿主语言原生的 async primitives 手写 loop，再用 Pydantic / Zod / Rust enum 等自建 tool schema。

0 / 11

没有对代码仓库做 Vector RAG

代码检索几乎全靠 ripgrep、glob、tree-sitter、LSP、文件路径和自动发现的 Markdown context。

原因：代码结构信息确定性强、变化快；预构建 embedding 很容易过期，且额外引入索引维护成本。

必须精确理解：论文并不是说“RAG 没用”，而是说 vector-embedding RAG 没被这些生产 Coding Agent 用来检索源码。OpenClaw 等系统依然可能对“对话记忆”使用 embedding/hybrid retrieval。

作者由此提出一个很有意思的判断：生产 Coding Harness 与通用 LLM Application 的复杂度预算不同。当系统真的要修改代码时，可调试性、prompt transparency 和结构确定性，往往比抽象复用更重要。

07Skills、MCP、ACP：论文观察到的协议与扩展趋势

9 / 11

SKILL.md

Skills 的采用率已经超过 MCP。作者把 Skill 看成“面向 LLM runtime 的 declarative program”：自然语言主体 + YAML metadata + 可选脚本。

8 / 11

MCP

MCP 已成为跨系统外部能力扩展的重要标准，但在这批 Harness 里，Skills 的覆盖面更高。

6 systems

ACP

ACP 不再只承担“IDE ↔ Agent”角色，还出现了第二种用途：把一个 Harness 当成另一个 Harness 的可替换 backend。

ACP 的三个角色

角色含义
Editor ↔ Agent像 LSP 一样，让 IDE 通过协议驱动本地 Agent。
Agent-as-backendOpenHands 等系统把 Claude Code / Codex / Gemini CLI 作为后端宿主。
Cross-vendor meshA2A 一类协议把不同 vendor 的 Agent 放进更大的 multi-agent topology。

非常关键的一点：Harness 内部自己的 sub-agent 通信，很多仍然是 in-process queue / function call / local session，并没有因为 ACP/A2A 出现就全部协议化。

08Platform Turn：为什么作者说 Harness 已经不是“工具”

作者的核心 thesis 是：2025 → 2026 年中，Harness 完成了从 CLI 工具到平台的转向。依据不是抽象判断，而是四个“平台信号”。

Signal 1 · Skills = Declarative Programs

Skill 有目录、说明、触发条件、权限和注册表，越来越像传统平台中的 package/plugin。

Signal 2 · Hooks / Event Bus = Extension Substrate

原本只在少数系统出现的生命周期 hook，到 7 月已经成为 9/11 系统的主流扩展方式。

Signal 3 · Tool 与 Workflow 的边界消失

Agent 不只是调用某个工具，而是接管“读代码 → 改代码 → 测试 → 提交 → 复核”的整段开发流程。

Signal 4 · Harness 变成 Service Surface

HTTP server、OpenAPI、SDK、Hosted Runtime、Managed Agents API 出现后，Harness 已经具备典型平台分发形态。

作者给出的第二种解释非常重要：生产 Harness 不使用 Agent Framework，不一定是因为它们“不需要框架”，而可能是因为 Harness 自己已经变成了框架。

09Minimalism Argument：100 行为什么也能打？

Mini-SWE-Agent 只有极小的 scaffold，却能报告与大型系统接近区间的 SWE-Bench Verified 表现。作者由此区分了两个问题：

“能不能完成任务”

Frontier model + 简单 loop + bash / file tools，很多情况下已经够。

≠

“能不能成为生产产品”

真正让代码量膨胀的是 safety、UX、recovery、cost control、extensions、clients、SDK、enterprise governance。

Scaffold–Capability Frontier

作者提出一个尚未证明的指导性假说：对固定任务和固定模型，scaffold complexity 与 task success 可能是近似“先陡升、后平台”的凹曲线。

没有 loop/tool：无法工作少量结构：快速增益复杂生产结构：收益转向安全/UX/可扩展
因此，生产 Harness 的复杂度不能只用 benchmark completion rate 来解释。很多工程投入根本不是为了让模型“更聪明”，而是为了让系统“更可用、更安全、更稳定”。

10Model–Harness Co-design：模型和 Harness 是双向塑形

Model shapes Harness

不同模型的 reasoning mode、tool-call behavior、edit reliability、cache semantics 不同，因此 prompt、tool contract、routing 与 context policy 会随模型族变化。

Harness shapes Model Usage

deferred tool loading、prompt cache boundary、compaction、thought stripping、provider routing 会改变模型实际看到的上下文、成本与行为。

这也是为什么 provider-native Harness 有天然优势：它们可以在模型版本更新当天，同时修改模型侧和 Harness 侧。多 Provider Harness 并非做不到优化，但需要自己维护 per-provider conditional layer。

11论文局限：哪些结论不能过度解释

只读源码，不跑统一实验

作者知道系统“怎么组织”，但不知道统一任务下谁更快、谁更稳定。Benchmark 数字大多来自项目自报。

定性比较仍有主观性

架构评分、模式归类包含研究者判断；虽然作者尽量用代码细节锚定，但不是完全客观指标。

Claude Code 可复现性较弱

它依赖一个公开流传的 2026 年 3 月源码 snapshot，并非官方完整开源 release，因此这一部分证据最弱。

“不存在”结论也不是数学证明

Framework absence 是基于 manifest/import grep；仍不可能绝对排除动态加载、内部 fork 或未观察到的路径。

所以这篇论文最适合支持的是：“截至作者固定的 2026 年 7 月版本，这 11 个系统的源码结构呈现出这些模式。” 不宜扩展成“所有 Agent 都应该这样做”。

13读完这篇后，真正应该留下的 8 个认知

① Harness 是 Runtime，不只是 Prompt Wrapper

真正的差异来自 loop、context、tool、安全、session 和 extension 的组合。

② 复杂 Loop ≠ 更高 Benchmark

Loop sophistication 更像 production readiness 的信号，而不是 task success 的直接预测器。

③ 生产 Coding Agent 偏爱 JIT Retrieval

代码检索依赖文件系统结构、ripgrep、tree-sitter、LSP，而不是预索引 vector RAG。

④ Framework Absence 是重要事实

这批产品普遍手写 native loop，但长期趋势又是 Harness 和 Framework 重新合并。

⑤ Skills 正在变成“Agent 软件包”

SKILL.md 不只是提示词文件，而正在具备 program/package 的结构属性。

⑥ Safety 是架构问题

从 prompt 里写“不要执行危险命令”远远不够，生产系统把安全下沉到 permission / policy / sandbox。

⑦ Model 与 Harness 必须共同演化

Harness 需要针对模型能力变化持续调整，而不是写完一次永久稳定。

⑧ Harness 正在平台化

SDK、hooks、marketplace、host、session import、meta-harness 的出现，说明类别边界已经发生变化。
